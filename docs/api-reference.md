# Exchange Engine — API Reference

Унифицированная абстракция над REST API и WebSocket биржами Binance, Bybit и OKX.
Все методы доступны через единый интерфейс `ExchangeClient`.

## Быстрый старт

```typescript
import { Exchange, ExchangeNameEnum } from '@solncebro/exchange-engine';

const exchange = new Exchange(ExchangeNameEnum.Binance, {
  config: { apiKey: 'YOUR_KEY', secret: 'YOUR_SECRET', isDemoMode: false },
  logger, // ExchangeLogger
});

const futures = exchange.futures; // ExchangeClient
const spot = exchange.spot;       // ExchangeClient

// Загрузить символы, получить тикеры, закрыть
await futures.loadTradeSymbols();
const tickers = await futures.fetchTickers();
await exchange.close();
```

## Фабрика Exchange

```typescript
class Exchange {
  readonly name: ExchangeNameEnum;
  readonly futures: ExchangeClient;
  readonly spot: ExchangeClient;

  constructor(name: ExchangeNameEnum, args: ExchangeArgs);
  getWebSocketConnectionInfoList(): WebSocketConnectionInfo[];
  close(): Promise<void>;
}
```

При `ExchangeNameEnum.Binance` создает `BinanceFutures` + `BinanceSpot`.
При `ExchangeNameEnum.Bybit` создает `BybitLinear` + `BybitSpot`.
При `ExchangeNameEnum.Okx` создает `OkxSwap` + `OkxSpot`. Для OKX обязательна кодовая фраза
(`ExchangeConfig.passphrase`): без неё конструктор `Exchange` сразу выбрасывает `ExchangeError`
с кодом `OKX_PASSPHRASE_REQUIRED`.

> - `resubscribeKlineList` на Binance Spot: пакетного варианта у потока нет — клиент переподписывает

> - `subscribeOrderbook` на Binance Futures: биржа отдаёт стакан только на глубине 5, 10 или 20.
>   Любая другая глубина отклоняется ошибкой, тогда как у Bybit и OKX набор глубин иной.
> - `unsubscribeOrderbook` / `resubscribeOrderbook` / `unsubscribePublicTrades` /
>   `resubscribePublicTrades` на Binance Spot и `unsubscribeRawOrderbook` на обоих рынках Binance:
>   подписки такого рода на этих рынках не бывает, а уборка и переподписка молчат намеренно —
>   отписываться от того, чего нет, безопасно, поэтому ошибки здесь нет.
> - `fetchFeeRate` на OKX: работает только с конкретным инструментом — вызов без `symbol`
>   отклоняется (`FEE_RATE_SYMBOL_REQUIRED`), общей ставки счёта у OKX в ответе нет.
> - `setMarginMode` на OKX Swap: биржа не хранит режим маржи как настройку инструмента. Метод
>   запоминает выбор в клиенте и подставляет его в каждую следующую заявку; открытую позицию он
>   не переводит в другой режим, а лишь предупреждает об этом в журнале. Если выбора не делали
>   (например, процесс только что перезапущен), клиент один раз спрашивает у биржи фактический
>   режим открытой позиции по инструменту и дальше пользуется им.

## Особенности OKX

Всё перечисленное — поведение самой биржи, спрятанное за общим интерфейсом. Знать это нужно
потому, что оно влияет на смысл чисел, а не только на способ вызова.

### Единицы: контракты и монеты

Бессрочный контракт OKX меряется штуками. Сколько монет в одной штуке, говорит сам инструмент
(поле `ctVal` в ответе списка инструментов; у BTC — 0.01 монеты), а минимальный шаг заявки — поле
`lotSz`. Биржа принимает объём ТОЛЬКО целым числом контрактов, кратным шагу.

Наружу библиотека говорит в монетах — как Binance и Bybit. Пересчёт делает клиент: объём заявки,
новый объём при правке, размер позиции, объём публичной сделки, ГЛУБИНА СТАКАНА (и разовый запрос,
и поток, и верх стакана в тикере), объём закрытой позиции и количество в записи журнала
начислений — всё это в монетах. Множитель берётся из карты, заполняемой при `loadTradeSymbols()`;
до её вызова заявка, глубина стакана, журнал начислений и итоги закрытых позиций отклоняются с
кодом `OKX_INSTRUMENTS_NOT_LOADED` — молча выдать контракты под видом монет библиотека не станет
нигде.

Объём меньше одного контракта — отказ (`AMOUNT_BELOW_LOT`), а не заявка нулевого размера: биржа
приняла бы такую как «ничего», и вызывающий считал бы, что защита стоит.

Торговый канал OKX адресует инструмент числовым кодом, который библиотека берёт из списка
инструментов, а биржа меняет при ПЕРЕЛИСТИНГЕ инструмента — после него нужен повторный
`loadTradeSymbols()`; до обновления карты заявки по такому инструменту идут обычными запросами
(они работают по имени), то есть медленнее, но не мимо.

`amountToPrecision` у контракта отвечает ровно тем числом, которое уйдёт на биржу: остаток сверх
целого числа контрактов отбрасывается (0.0157 монеты BTC — это 0.01), а размер меньше одного
контракта возвращается нулём. Созданная заявка (`Order.amount`) несёт тот же фактически
отправленный размер, а не тот, о котором просили.

Верх стакана в тикере (`bid1Size`/`ask1Size`) у инструмента, которого нет в карте множителей,
не заполняется вовсе: пустое поле честнее числа, ошибающегося во столько раз, сколько монет в
контракте.

У спота пересчёта нет: там объём и так в монетах.

### Имена инструментов

Снаружи — общие имена (`BTCUSDT`). Внутри клиент переводит их в обозначения OKX: `BTC-USDT-SWAP`
для бессрочного контракта, `BTC-USDT` для спота, и обратно в ответах. Имя, которого нет в
загруженной карте, разбирается по известным котируемым валютам (USDT, USDC); если и так не
получается — `OKX_SYMBOL_UNRESOLVED`. Обозначение чужого рынка (спотовое у клиента контрактов и
наоборот) отвергается тем же кодом, а не молча принимается.

### Кодовая фраза

OKX подписывает каждый запрос тройкой «ключ, секрет, кодовая фраза». Поэтому
`ExchangeConfig.passphrase` для OKX обязателен, и клиент отказывается создаваться без неё —
сразу, в конструкторе, а не при первом запросе.

### Условные заявки идут через отдельную службу биржи

Стоп, тейк и скользящий стоп у OKX живут не в обычной книге заявок, а в отдельной службе, со
своей нумерацией. Практические следствия:

- Номер условной заявки в обычной книге не существует, и наоборот. Клиент помнит происхождение
  каждого номера (по паре «инструмент + номер», не дольше суток) и адресует чтение, отмену и
  правку сразу в нужную службу.
- Номер, происхождение которого неизвестно — например, пришедший извне после перезапуска
  процесса, — спрашивается у обеих служб один раз, после чего запоминается. Если ответили обе,
  клиент отказывается выбирать (`CONDITIONAL_ORDER_ID_AMBIGUOUS`): вернуть чужую заявку хуже,
  чем не вернуть никакой.
- Вход биржи для условных заявок принимает ТОЛЬКО номер — инструмент ему не задать, поэтому
  ответить он может по любому инструменту счёта. Клиент сверяет инструмент в ответе с тем, о
  котором спрашивали, и чужой считает за «такой заявки по этому инструменту нет»: иначе наружу
  ушла бы чужая заявка с объёмом, пересчитанным множителем НАШЕГО контракта, её номер запомнился
  бы под нашим именем, и следующая отмена сняла бы чужую защиту.
- Правка с триггерной ценой, равной нулю (в том числе округлившейся до нуля шагом инструмента),
  отклоняется до отправки (`STOP_PRICE_REQUIRED`) — тем же кодом, что и постановка без цены. У
  OKX ноль в этом поле означает не «цену не задали», а «стоп удалить», и биржа ответила бы на это
  успехом: просьба подвинуть стоп сняла бы защиту. Это верно и для ПАКЕТНОЙ правки: такая запись
  получает свой исход-отказ, на биржу не отправляется, остальные записи пачки правятся как обычно.
- Правка условной заявки с новой триггерной ценой узнаётся по самой триггерной цене, а не только
  по памяти — иначе после перезапуска «подвинуть стопы» уходило бы в обычную книгу.
- Торговый канал условные заявки не принимает: они всегда идут обычным запросом. Пакетного входа
  у этой службы тоже нет — условные заявки из пачки ставятся по одной, а исход каждой всё равно
  кладётся на своё место входного списка.
- Уже сработавшая условная заявка порождает обычную; при чтении клиент дочитывает фактическое
  исполнение из неё и складывает в один ответ. Сама сработавшая заявка считается ОТКРЫТОЙ, как у
  Binance и Bybit: срабатывание — это ещё не исполнение, порождённая заявка может исполниться
  частично или получить отказ. Своего исполнения у условной заявки нет — средняя цена и
  заполненный объём остаются нулями, пока не прочитана порождённая заявка.
- У заявки «одна отменяет другую» заполнены обе ноги, а `Order` несёт только одну пару «тип +
  цена + триггер». Наружу отдаётся нога защиты от убытка — и правка идёт в ту же ногу, что
  показало чтение. Если биржа сообщила, какая нога фактически сработала (`actualSide`), берётся
  она.
- Скользящий стоп биржа править не умеет вовсе («Support Stop order and Trigger order only, not
  including Move_order_stop order»): попытка отклоняется кодом
  `OKX_TRAILING_STOP_AMEND_UNSUPPORTED`, такую заявку надо снять и поставить заново.
- Правка ТОЛЬКО по объёму не несёт триггерной цены, поэтому после перезапуска процесса она
  сначала уходит в обычную книгу; получив от биржи «такой заявки нет», клиент повторяет её в
  условной службе и запоминает происхождение.
- «Биржа ответила: такой заявки нет» и «спросить не удалось» — разные исходы, и клиент их не
  путает ни при чтении, ни при отмене, ни при правке. Пока обе службы отвечают отсутствием,
  наружу идёт «заявки нет». Если хоть одна не ответила по связи, наружу идёт этот сбой со своей
  исходной причиной, а причина каждого отказа пишется в журнал. Иначе вызывающий счёл бы
  защитную заявку снятой и либо поставил вторую, либо закрыл позицию, тогда как заявка на бирже
  жива.

### Режим маржи после перезапуска процесса

Биржа не отдаёт режим маржи как настройку инструмента, а ручка «узнать плечо» принимает режим
вводом и лишь возвращает его эхом — то есть режима не называет. Фактический режим несёт сама
открытая позиция, поэтому при первой заявке по инструменту, о котором клиент ничего не помнит,
он один раз спрашивает позиции ВСЕГО СЧЁТА и заполняет память сразу по всем инструментам. Раньше
после перезапуска любая заявка уходила как «общая маржа», и по позиции, которую биржа держит
изолированной, биржа отвергала каждую заявку, включая защитную; а чтение по одному инструменту
давало пачке из двадцати символов двадцать запросов подряд до отправки первой заявки. Инструмент
без открытой позиции считается общим; если спросить не удалось, в журнал идёт предупреждение,
заявка уходит с прежним умолчанием, а следующая спросит заново.

Оговорка: память счётная, поэтому изолированная позиция, открытая руками ПОСЛЕ этого снимка по
инструменту, которого клиент ещё не касался, замечена не будет. Явный `setMarginMode` по-прежнему
сильнее прочитанного.

### Спот и сумма в котируемой валюте

`quoteOrderQty` (или `marketUnit: quoteCoin`) означает «купить на столько-то долларов». OKX
принимает это только на РЫНОЧНОМ исполнении спота: на лимитном та же сумма стала бы количеством
монет, поэтому клиент отказывает (`QUOTE_AMOUNT_MARKET_ONLY`).

К бессрочному контракту сумма в котируемой валюте не применяется вовсе — там поле объёма означает
число контрактов, и сто долларов уехали бы на биржу как сто контрактов. Единица объёма (`tgtCcy`)
по той же причине ставится только на споте.

### Режим маржи — память клиента, а не настройка биржи

У OKX режим маржи задаётся в каждой заявке, отдельной настройки инструмента нет. `setMarginMode`
запоминает выбор по инструменту и подставляет его во все последующие заявки. Умолчание — общая
маржа; после перезапуска процесса память пуста. Если по инструменту уже открыта позиция в другом
режиме, метод пишет предупреждение в журнал: сменить режим под открытой позицией биржа не даёт.

Изолированной маржи не существует на счетах в режимах «многовалютная маржа» и «портфельная маржа»
(режимы счёта 3 и 4): биржа отвергла бы КАЖДУЮ последующую заявку. О таком сочетании
`setMarginMode` предупреждает сразу, в момент выбора.

### `triggerDirection` игнорируется

Поле «с какой стороны цена подходит к уровню» OKX не принимает — биржа выводит направление сама
из того, какая нога условной заявки заполнена и с какой стороны стоит заявка. Значение просто не
попадает на провод.

### Объём торгов за сутки по контрактам — оценка

По бессрочным контрактам OKX отдаёт оборот только в базовой валюте. `Ticker.quoteVolume` для
контракта получается умножением на ПОСЛЕДНЮЮ цену — это расчёт, а не число биржи. У Binance и Bybit
на том же месте лежит факт, посчитанный биржей по каждой сделке. У монеты, выросшей за сутки
втрое, отношение последней цены к средневзвешенной около двух — то есть оценка завышена примерно
вдвое, и отбор с порогом «оборот за сутки больше N» на OKX пропустит неликвид ровно на разгоне,
там, где порог и был нужен. У спота обе величины приходят с биржи как есть.

### Цена маркировки, индекс и фандинг в тикере OKX пусты

Ответ тикеров OKX этих полей не содержит вовсе, поэтому `Ticker.markPrice`, `Ticker.indexPrice`,
`Ticker.fundingRate` и `Ticker.nextFundingTime` на OKX не заполняются НИКОГДА (у Bybit заполнены
все четыре). Сшивать их в каждый вызов тикеров библиотека не станет: это два лишних запроса на
каждый вызов. Кому нужны эти числа — `fetchMarkPrice()` (цена маркировки, индекс, ставка и время
следующего фандинга одним вызовом) и `subscribeMarkPrices()` для потока.

Следствие для приёма «премия из тикера» (`mid − mark`, описан в разделе про `subscribeAllTickers`):
на OKX он не работает — цена маркировки берётся из `fetchMarkPrice`/`subscribeMarkPrices`.

### Индексная цена: в разовом чтении есть, в потоке — нет

Ответ цены маркировки OKX индекса не несёт, поэтому `fetchMarkPrice()` берёт его ОТДЕЛЬНЫМ
запросом (`/api/v5/market/index-tickers`) и сшивает по обозначению: индекс — это контракт без
хвоста `-SWAP` (`BTC-USDT-SWAP` → `BTC-USDT`). Без символа индексы спрашиваются по каждой валюте
расчёта (USDT и USDC) одним ответом на валюту. Отказ этой ручки цену маркировки не срывает: она
вернётся без индекса и с предупреждением в журнале.

Индекса нет в ответе — `MarkPrice.indexPrice` остаётся ПУСТЫМ, никогда не нулём: поддельный ноль
молча отключил бы у потребителя составляющую `Max(Индекс, …)` в расчёте границы цены.

В ПОТОКЕ индекс по-прежнему неизвестен: канал цены маркировки несёт только её саму, и отдельный
канал индекса библиотека пока не подписывает. `MarkPriceUpdate.indexPrice` на OKX пуст.

### Граница цены заявки

OKX отдаёт границы цены процентами в том же ответе списка инструментов, и `TradeSymbol.priceLimitRisk`
их несёт с пометкой источника `okxPriceLimitPct`: начальная граница первых десяти минут после
листинга, плавающая граница обычной торговли и потолок отклонения от индекса. Все три — в
ПРОЦЕНТАХ: биржевое «0.03 represents 3%» приходит наружу как `3`. Величина, которой биржа не дала
(у опционов и событий приходят пустые строки), остаётся пустой строкой; если пусты и плавающая
граница, и потолок, поля `priceLimitRisk` нет вовсе.

### Минимального номинала заявки OKX не отдаёт

`getMinNotional(symbol)` на OKX всегда 0. В ответе списка инструментов есть минимальное
КОЛИЧЕСТВО (`minSz`) и шаг (`lotSz`), но величины в деньгах нет ни одной — минимального номинала
биржа не публикует вовсе. Проверка «заявка не меньше минимальной суммы», написанная один раз на
все биржи, на OKX пропустит всё, и отказ придёт уже от биржи. У Binance и Bybit это реальное
число биржи.

### «Снять всё» снимает условные заявки всех видов

Открытые условные заявки OKX отдаёт ПО ВИДАМ, и один запрос принимает перечисление через запятую
только для пары «стоп/тейк, ОСО» — остальные виды требуют своего запроса. Поэтому и
`cancelAllOrders(symbol)`, и `fetchOpenConditionalOrders(settleCoin)` спрашивают биржу столько раз,
сколько видов она умеет отдавать: стоп/тейк и ОСО, скользящий стоп, плановая заявка, айсберг,
заявка по времени, умный айсберг и — только у контрактов — заявка-преследование. Заявка,
поставленная человеком в приложении биржи, снимается наравне со своими.

**Отказ биржи по одному виду не рвёт работу и не проходит молча.** Каждый такой отказ пишется в
журнал предупреждением (вид заявки и причина), обход остальных видов продолжается. Дальше две
биржи ведут себя по-разному по существу дела:
- `cancelAllOrders(symbol)` снимает всё, что нашлось, и ТОЛЬКО потом, если хоть один вид отказал,
  бросает исключение с кодом `OKX_CANCEL_ALL_INCOMPLETE` и перечнем несделанного. Читать это
  исключение как «ничего не произошло» нельзя: часть работы сделана, и перечень говорит какая
  именно осталась. Метод возвращает `void`, поэтому сказать о неполноте больше нечем — но говорит
  он о ней, уже сделав всё, что мог;
- `fetchOpenConditionalOrders(settleCoin)` при отказе по любому виду отказывает целиком
  (`OKX_CONDITIONAL_ORDERS_INCOMPLETE`): короткий список защитных заявок вы прочитали бы как
  «стопов нет».

Цена честности: на пути отказа тратятся все семь запросов ручки условных заявок, а её предел —
20 запросов за 2 секунды на пользователя.

### Клиентский номер заявки

Только латинские буквы и цифры, не длиннее 32 знаков. Дефисы, подчёркивания и двоеточия биржа не
принимает, поэтому клиент отклоняет такой номер до отправки
(`OKX_CLIENT_ORDER_ID_INVALID`).

### Журнал начислений: одна запись сделки — две строки

Запись журнала о сделке несёт сразу два вида начисления: реализованный итог (поле `pnl`) и
торговую комиссию (поле `fee`). Поэтому без фильтра такая запись раскладывается на ДВЕ строки —
`realizedPnl` с ВАЛОВЫМ итогом и `commission` с комиссией, — то есть ровно на те же строки, что
вернут два запроса с фильтрами. Общее изменение остатка (`balChg`) за реализованный итог не
выдаётся: оно уже за вычетом комиссии. Запись сделки, где ни итога, ни комиссии нет, отдаётся
видом `other`, чтобы журнал не терял записи молча.

### Остаток кошелька и капитал счёта — разные числа

Биржа отдаёт только капитал счёта (`totalEq`, вместе с нереализованным итогом по открытым
позициям). Наружу идут оба смысла: `AccountBalances.totalMarginBalance` — капитал как есть,
`totalWalletBalance` — денежный остаток БЕЗ плавающей прибыли и убытка, как его понимает Binance.
Без этого правило риска «остановить торговлю, если кошелёк за сутки просел» срабатывало бы на OKX
от живого убытка по открытой позиции, а на Binance в том же положении молчало.

Нереализованный итог для вычитания берётся ПО МОНЕТАМ и переводится в доллары курсом самой монеты.
Сводное поле счёта для этого не годится: биржа считает в нём только позиции с ОБЩЕЙ маржой и не
заполняет его вовсе в двух режимах счёта из четырёх — «простом» и «одновалютном», а бессрочные
контракты в одновалютном торгуются. На поле монеты этих ограничений нет: оно есть в каждом режиме,
где бессрочные контракты вообще доступны, и считает обе маржи — общую и изолированную. Оговорка
честности: если у монеты с ненулевым плавающим итогом биржа не дала курса, перевести нечем — тогда
в дело идёт сводное поле счёта, а если пусто и оно, остаток кошелька совпадёт с капиталом.

На уровне ОТДЕЛЬНОЙ монеты паритета нет: `Balance.total` у OKX — капитал монеты (`eq`),
`Balance.walletBalance` — её денежный остаток (`cashBal`).

### Итоги закрытых позиций: строка НАКОПИТЕЛЬНАЯ, складывать её по окнам нельзя

`fetchClosedPnl` у OKX читает историю ПОЗИЦИЙ, и это другой смысл строки, чем у соседей. У Binance
строка — одна закрывающая заявка, у Bybit — одна запись закрытия; строки разных окон не
пересекаются, и посуточное суммирование даёт верный итог за период.

У OKX строка одна на ВСЮ ЖИЗНЬ позиции и ОБНОВЛЯЕТСЯ при каждом частичном закрытии: биржа сама
называет свои поля накопительными («Position's cumulative closed volume», «Accumulated fee»,
«It is the latest type if there are several types for the same position»), а страницы адресует
временем ОБНОВЛЕНИЯ (`uTime`).

Что это значит на практике. Позиция открыта в понедельник, половина закрыта в понедельник (итог
10), вторая половина во вторник (ещё 15). Запрос за понедельник вернёт эту позицию с итогом 10,
запрос за вторник — ЕЁ ЖЕ с итогом 25. Кто складывает посуточно (обычный способ построить кривую
доходности), получит 35 вместо 25. **Итоги OKX по окнам не складывают — берут последнее значение
по номеру позиции.** Отличить строки одной позиции можно по полю `orderId`: у OKX там номер
ПОЗИЦИИ (`posId`), а не заявки — своего номера заявки у этой записи биржа не даёт, и сверить итоги
с историей заявок по нему не получится.

Побочно: строка OKX может относиться к ещё ОТКРЫТОЙ позиции (частичное закрытие), то есть итог в
ней не окончателен — на соседях такого не бывает. Библиотека ничего из этого не «чинит»: так
устроен ответ биржи.

### Границы крупных свечей — всемирное время, как у соседей

У OKX два набора обозначений для свечей от шести часов и крупнее: без суффикса свеча режется от
полуночи по UTC+8 (то есть от 16:00 всемирного времени), с суффиксом `utc` — от полуночи
всемирного времени. Библиотека запрашивает ТОЛЬКО второй набор (`6Hutc`, `12Hutc`, `1Dutc`,
`3Dutc`, `1Wutc`, `1Mutc`) — и в разовом чтении, и в потоке, — поэтому шести- и двенадцатичасовые,
дневные, трёхдневные, недельные и месячные свечи OKX выровнены с Binance и Bybit: одна и та же
свеча на трёх биржах открывается в один и тот же миг. Интервалы в четыре часа и мельче этой
особенности не имеют — их сетка делит восьмичасовой сдвиг нацело.

## 1. Инструменты и конфигурация

### `loadTradeSymbols()`

```typescript
loadTradeSymbols(): Promise<TradeSymbolBySymbol>
```

Загружает список торговых инструментов с биржи, заполняет `tradeSymbols`. При повторном вызове очищает и перезагружает данные.

```typescript
const symbols = await futures.loadTradeSymbols();
```

```typescript

```

Округляет количество до шага `stepSize` инструмента. Требует предварительного вызова `loadTradeSymbols()`.

```typescript
const qty = futures.amountToPrecision('BTCUSDT', 0.00156);
```

### `fetchAllKlines()`

```typescript
fetchAllKlines(
  symbolList: string[],
  interval: KlineInterval,
  options?: FetchAllKlinesOptions,

```

Параллельная загрузка свечей для списка символов с разбивкой на чанки.

| Параметр | Тип | Обязательный | Описание |
|---|---|:---:|---|

### `fetchIncome()`

```typescript
fetchIncome(options?: FetchIncomeArgs): Promise<Income[]>
```

Получает историю доходов/расходов (комиссии, фандинг, PnL).

| Параметр | Тип | Обязательный | Описание |
|---|---|:---:|---|
| `options` | `FetchIncomeArgs` | нет | `startTime`, `endTime`, `limit`, `incomeType?: 'funding'` |

С `incomeType`, равным `'funding'` / `'realizedPnl'` / `'commission'`, возвращаются только записи этого вида. Binance фильтрует на стороне биржи (`incomeType=FUNDING_FEE`/`REALIZED_PNL`/`COMMISSION`). Bybit пробрасывает окно времени в журнал транзакций и фильтрует локально; `limit` клампится к 50 (максимум журнала), а если сырой ответ упёрся в лимит страницы — метод бросает ошибку, чтобы не вернуть неполную сумму.

**Без `incomeType` (07.09.2026) возвращаются ВСЕ ТРИ вида разом, каждая запись помечена полем `kind`** — раньше потребителю, которому нужны все три потока, приходилось делать три отдельных запроса, и на Bybit все три уходили за одной и той же страницей одного и того же журнала операций. У Bybit одна запись `SETTLEMENT` законно даёт до трёх строк результата (начисление фандинга и денежный поток сделки лежат в разных полях одной записи биржи), результат отсортирован по времени по возрастанию. У Binance каждая сырая запись даёт ровно одну строку, `kind` резолвится обратным переводом `incomeType` (`resolveBinanceIncomeKind`); значение, которого нет среди трёх известных видов, получает `kind: 'other'`.

Сумма фандинга у Bybit берётся из поля `funding` строки журнала: денежный поток (`cashFlow`) у начисления фандинга нулевой (живой счёт 02.09.2026). Знак одинаков на обеих биржах — отрицательное значит списано.

**Возврат:** `Income[]` — массив записей, каждая с полем `kind: IncomeKind` (`'realizedPnl' | 'commission' | 'funding' | 'other'`).

| Биржа | Futures | Spot |
|---|:---:|:---:|
| Binance | ✅ | ❌ |
| Bybit | ✅ | ✅ |

### `fetchClosedPnl()`

```typescript
fetchClosedPnl(symbol?: string, options?: FetchPageWithLimitArgs): Promise<ClosedPnl[]>
```

Получает историю закрытых PnL.

| Параметр | Тип | Обязательный | Описание |
|---|---|:---:|---|
| `symbol` | `string` | нет | Символ для фильтрации |
| `options` | `FetchPageWithLimitArgs` | нет | `startTime`, `endTime`, `limit` |

**Возврат:** `ClosedPnl[]` — массив закрытых PnL.

`limit` на обеих биржах значит одно и то же: **сколько строк ИТОГА вернуть**. Это не мелочь: у Bybit есть готовая ручка закрытых позиций, а у Binance такой ручки нет вовсе — итоги собираются из сырых исполнений счёта, и раньше `limit` уезжал прямо туда, превращаясь в «столько исполнений». Рыночное закрытие неликвида биржа дробит на сотни исполнений, поэтому потребитель получал итог меньше половины сделки и записывал его как факт биржи.

`closedPnl` на обеих биржах — итог ЧИСТЫЙ после торговых комиссий (открытия и закрытия), но БЕЗ фандинга: фандинг — отдельный поток начислений (`fetchIncome`, `incomeType: 'funding'`), потребитель складывает их сам. У Binance итог собирается из исполнений; у Bybit — из полей записи закрытия (`cumEntryValue − cumExitValue − openFee − closeFee`), потому что биржевое поле `closedPnl` там уже включает фандинг за жизнь позиции (проверено 02.09.2026 на 7 закрытиях подряд). Тождество «валовой − closedPnl = комиссии» держится на обеих биржах.

У OKX история закрытых позиций тоже читается постранично (страницы адресуются отметкой закрытия),
поэтому ответ больше не обрывается молча на сотой записи.

**Просите окно по времени, а не число строк.** С заданным `startTime` Binance-клиент забирает исполнения постранично (страница — потолок биржи в 1000; следующие адресуются номером сделки, потому что биржа запрещает сочетать его с окном) и отдаёт полный итог. Без `startTime` берётся одна страница максимального размера — этого может не хватить на дроблёное закрытие.

| Биржа | Futures | Spot |
|---|:---:|:---:|
| Binance | ✅ | ❌ |
| Bybit | ✅ | ✅ |

### `getOrderRateLimit()`

```typescript
getOrderRateLimit(): Promise<OrderRateLimit>

interface OrderRateLimit {
  writeRequestsPerSecond: number;
  source: OrderRateLimitSource;
}

type OrderRateLimitSource =
  | 'binance-exchange-info'
  | 'bybit-exchange-header'
  | 'bybit-documented'
  | 'okx-documented'
  | 'fallback';
```

Возвращает per-UID write rate-limit для order endpoints (create/cancel/modify, в т.ч. batch). Используется потребителями для динамической настройки throttling/queueing logic.

**Поведение per биржа/рынок:**

| Биржа/Рынок | Источник | Значение |
|---|---|---|
| Binance Futures | `binance-exchange-info` — парсинг из `GET /fapi/v1/exchangeInfo` (`rateLimits[]` с `rateLimitType: 'ORDERS'`, минимум по всем интервалам в RPS) | реальное (зависит от аккаунта/тарифа) |
| Binance Spot | `binance-exchange-info` — то же из `GET /api/v3/exchangeInfo` | реальное |
| Bybit Linear / Spot | `bybit-exchange-header` — предел, названный самой биржей в заголовке ответа на заявку (`X-Bapi-Limit`), запомненный торговым каналом | реальное |
| Bybit Linear | `bybit-documented` — запасной вариант, пока биржа ни одного заголовка не назвала | `10` RPS |
| Bybit Spot | `bybit-documented` — то же | `20` RPS |
| OKX Swap / Spot | `okx-documented` — документированный предел НА ИНСТРУМЕНТ (60 запросов за 2 секунды) | `30` RPS |
| Fallback | `fallback` — Binance не вернул `rateLimits[]` или массив `ORDERS`-лимитов пуст | `15` RPS (`BINANCE_ORDER_RATE_LIMIT_FALLBACK_RPS`) |

| Биржа | Futures | Spot |
|---|:---:|:---:|
| Binance | ✅ | ✅ |
| Bybit | ✅ | ✅ |
| OKX | ✅ | ✅ |

```typescript
const limit = await exchange.futures.getOrderRateLimit();
console.log(`Write RPS: ${limit.writeRequestsPerSecond}, source: ${limit.source}`);
// → "Write RPS: 300, source: binance-exchange-info"   (пример Binance Futures)
// → "Write RPS: 17,  source: bybit-exchange-header"   (Bybit, биржа уже назвала предел)
// → "Write RPS: 10,  source: bybit-documented"        (Bybit Linear, заголовка ещё не было)
```

**Замечание для Bybit:** Bybit не отдаёт rate-limits через GET endpoint — только через response headers на actual order calls. Торговый канал запоминает этот заголовок после ЛЮБОЙ операции с заявкой (одиночной и пачкой), и метод отдаёт живое число с источником `bybit-exchange-header`. Пока ни одной операции не прошло, возвращается документированная константа `bybit-documented` (источник: https://bybit-exchange.github.io/docs/v5/rate-limit).

| Параметр | Тип | Обязательный | Описание |
|---|---|:---:|---|
| `argsList` | `ResubscribeKlinesArgs[]` | да | Символ и размер свечи для каждого потока |

Пакетом отправляют Binance Futures, Bybit и OKX. На Binance Spot пакетного варианта нет — клиент переподписывает по одному; результат тот же, но одной командой это не сделать.

### `subscribeOrderbook()`

```typescript
subscribeOrderbook(args: SubscribeOrderbookArgs): void
```

Подписывается на обновления стакана. Уровни передаются как сырые пары decimal-строк (`OrderBookRawLevel = [string, string]`), чтобы избежать потери точности при разборе в число.

| Параметр | Тип | Обязательный | Описание |
|---|---|:---:|---|
| `args.symbol` | `string` | да | Торговый символ |
| `args.depth` | `number` | да | Глубина стакана. Наборы у бирж РАЗНЫЕ — см. таблицу ниже |
| `args.handler` | `OrderBookHandler` | да | `(symbol: string, update: OrderBookUpdate) => void` |

| Рынок | Поведение |
|------|-----------|
| Binance Futures | Поток `{symbol}@depth{depth}@100ms` на отдельном соединении. Биржа отдаёт стакан ТОЛЬКО на глубине `5`, `10` или `20` — любая другая отклоняется ошибкой |
| Binance Spot | Не поддерживается: вызов бросает `Orderbook subscription not supported for spot market` |
| Bybit Linear / Spot | Топик `orderbook.{depth}.{symbol}`; в обработчик приходят и полный снимок, и приращения. Глубины: linear — `1` / `50` / `200` / `500` / `1000`, spot — `1` / `50` / `200` |
| OKX Swap / Spot | Канал выбирается по запрошенной глубине: `1` — верх стакана, до `5` — пятиуровневый, глубже — полный канал, который всегда отдаёт свою предельную глубину независимо от запроса (об этом пишется предупреждение) |

```typescript
bybitLinear.subscribeOrderbook({
  symbol: 'BTCUSDT',
  depth: 50,
  handler: (symbol, update) => {
    if (update.updateType === 'snapshot') {
      // reset local book
    }
    // bidList/askList — массив пар [priceString, quantityString]
  },
});
```

### `setOrderbookLiveSymbol()`

```typescript
setOrderbookLiveSymbol(args: SetOrderbookLiveSymbolArgs): void
```

Помечает символ как «сейчас нужен в разобранном виде». Относится только к отложенному разбору стакана (`lazyOrderbookParse` в настройках): при нём кадры стакана по умолчанию НЕ разбираются, а раздаются потребителю сырыми. Помеченный символ разбирается полностью, как обычно.

| Параметр | Тип | Обязательный | Описание |
|---|---|:---:|---|
| `args.symbol` | `string` | да | Торговый символ |
| `args.isLive` | `boolean` | да | `true` — разбирать полностью, `false` — вернуть в сырой режим |

Только Bybit и OKX. На обоих рынках Binance — ошибка: обещать доставку данных и молча её не выполнить хуже, чем отказать сразу.

### `subscribeRawOrderbook()`

Binance futures income не содержит этого поля. `kind` — приведённый к общему смыслу вид дохода, не зависящий от сырого названия биржи (`REALIZED_PNL`, `TRADE`, `SETTLEMENT`…); `'other'` — всё, что не относится ни к одному из трёх торговых потоков (переводы, начисления).

#### `ExchangeError`

```typescript
class ExchangeError extends Error {
  readonly code: number | string;
  readonly exchange: string;

  constructor(message: string, code: number | string, exchange: string);
}
```

Выбрасывается при ошибках API биржи. Поле `code` содержит код ошибки биржи, `exchange` — имя биржи.

```typescript
import { ExchangeError } from '@solncebro/exchange-engine';

try {
  await futures.createOrderWebSocket(args);
} catch (error) {
  if (error instanceof ExchangeError) {
    console.log(error.code, error.exchange, error.message);
  }
}
```
