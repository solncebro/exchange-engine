# Живые проверки биржи

В каталоге два скрипта, и они отвечают на РАЗНЫЕ вопросы:

| Скрипт | Вопрос, на который отвечает |
|---|---|
| `exchange-live-check.ts` (`yarn exchange:live-check`) | Держит ли биржа один и тот же ДОГОВОР на всех трёх биржах: единицы, знаки, порядок, инварианты, потоки. Одни и те же обещания прогоняются по Binance, Bybit и OKX, чтобы расхождение между ними стало видно. |
| `okx-live-probe.ts` (`yarn okx:probe`) | Верно ли ДЕСЯТЬ конкретных утверждений про OKX, которые нельзя доказать чтением документации. Только OKX, каждое утверждение с дословным ответом биржи. |

## Граница с `trade-engine`: что где проверяется

Одно и то же обещание не проверяется дважды.

- **`exchange-engine` (этот каталог)** — договор БИРЖИ на уровне библиотеки: единицы объёма (монеты, а не
  контракты), знак комиссии, отметка времени в миллисекундах, порядок свечей и уровней стакана,
  инварианты баланса, приход кадров в публичные потоки, оборот одной заявки через публичный
  `ExchangeClient`.
- **`trade-engine` (`../trade-engine/tests/integration/{binance,bybit,okx}.test.ts`)** — логика ОБЁРТКИ:
  разрешение имён с приставками (`FLOKIUSDT` → `1000FLOKIUSDT`), запасной путь через спот, `ExchangeConnector`,
  `PositionManager` (чтение состояния позиции, открытие и закрытие рынком, установка плеча),
  расчёт закрывающих заявок.

Здесь НЕ проверяется ничего из второго списка, там — ничего из первого.

## `exchange-live-check` — договор с биржей на трёх биржах

### Ключи

Ключи трёх бирж живут в файле `.env` ЭТОЙ библиотеки — рядом с `package.json`, по образцу
`.env.example` (сам `.env` уже в `.gitignore`). Имя на биржу ровно одно, других наборов скрипт не
знает:

| Биржа | Имена переменных |
|---|---|
| Binance | `BINANCE_API_KEY`, `BINANCE_SECRET` |
| Bybit | `BYBIT_API_KEY`, `BYBIT_SECRET` |
| OKX | `OKX_API_KEY`, `OKX_SECRET`, `OKX_PASSPHRASE` |

Файл читает собственный разборщик `scripts/live-support/liveEnvFile.ts` — пакета `dotenv` в
зависимостях нет и ставить его нельзя. Он понимает строки `KEY=VALUE` и `export KEY=VALUE`,
снимает кавычки по краям значения и пропускает пустые строки и строки с `#` в начале.
**Переменная оболочки сильнее файла:** уже заданное имя из файла не перезаписывается. Первой
строкой прогона скрипт печатает, найден ли файл, сколько имён из него взято и какие имена задала
оболочка, — только имена, значения не печатаются нигде.

Поэтому запуск — одна команда, без `source`:

```bash
yarn exchange:live-check
```

Без ключей скрипт всё равно запускается: публичные обещания (инструменты, тикеры, свечи, стакан,
цена маркировки, предел частоты, потоки) прогоняются, приватные помечаются «не выполнена» с
названиями недостающих переменных. Код выхода при этом 0 (см. «Код выхода»). У OKX кодовая фраза нужна уже
конструктору клиента, поэтому без неё все обещания OKX помечаются «не выполнена».

### Только демо-счета

`isDemoMode: true` ставится всегда и ключом не переключается; все живые проверки ходят только на
демо-счета, боевого режима у скриптов нет.

### Ключи запуска

| Ключ | Что делает |
|---|---|
| `--exchange=binance,bybit,okx` | Отбор бирж. По умолчанию — все три. |
| `--only=<кусок текста>` | Прогнать только те обещания, в чьём названии встречается этот текст. Номер обещания в выводе остаётся номером из таблицы ниже, а не порядковым номером среди отобранных. |
| `--allow-orders` | Разрешает обещаниям 14–17 ставить заявки и менять настройки демо-счёта — на всех трёх биржах (подробности в «Безопасности»). |
| `--verbose` | Печатать ещё и журнал библиотеки (потоки, повторы, отказы). |

### Статусы

`подтв.` — обещание держится. `не прим.` — обещание к этой бирже не применимо: величины, о которой
оно говорит, биржа не отдаёт вовсе, поэтому чинить нечего. `расх.` — биржа отвечает не так, как
обещано (это и есть находка). `неполн.` — проверка отработала, но условий для вывода не сложилось.
`неудача` — сорвалось на отказе биржи или связи. `пропуск` — не выполнялась (нет ключей, нет
`--allow-orders`).

**Не применимо — не поблажка.** Единственный такой случай сейчас — долларовая оценка монеты в
обещании 9. Она объявлена НЕОБЯЗАТЕЛЬНОЙ, и фьючерсный ответ Binance её не несёт ни по одной
монете: взять её там неоткуда. Правило работает по принципу «всё или ничего»: нет ни у одной
ненулевой монеты — «не применимо» с прямым текстом, что свод по монетам на этой бирже не проверить;
есть у части монет — по-прежнему `расх.`, потому что неполный свод хуже отсутствующего. Остальные
условия обещания (свободных не больше капитала, источник назван, по монете свободных не больше её
капитала) проверяются в любом случае, и их нарушение остаётся расхождением.

**Данные биржи — не расхождение библиотеки.** Обещание про инструменты различает два случая. Если
шага цены, шага объёма или наименьшего объёма нет у инструмента, которым биржа сама торговать пока
не даёт (`PENDING_TRADING` у Binance и то же по смыслу у соседей), это её собственные данные:
такие записи печатаются отдельной строкой «данные биржи» и статус не портят. Отдельно так же
считается отсутствующий наименьший объём при заданном шаге объёма — шаг и есть настоящий пол
(`TUSDT` на Binance: минимум `0`, шаг `1`). Расхождением остаётся только то, что мешает поставить
заявку по инструменту, которым биржа торгует прямо сейчас.

То же различение — у тикеров. Процент изменения сверяется НЕ по величине, а по арифметике: он
обязан совпадать с ростом от цены на начало суток к последней с допуском в сотую долю процентного
пункта (у величин порядка 10¹⁴ допуск берётся миллионной долей самой величины — там уже шаг
двоичной дроби крупнее сотой доли пункта). Инструмент, по которому за сутки не было ни одной сделки
или нет цены на начало суток, сверять не с чем: он идёт строкой «данные биржи» с обозначением и
статус не портит. Отметка времени старше недели у инструмента, которым биржа торговать НЕ даёт, —
замороженные сутки. У инструмента, который биржа числит торгуемым, такая отметка сверяется с его
последней сделкой (`fetchTrades`): если и сделка старше недели, а отметка не раньше неё, это
«торгуемый без сделок» — строка «данные биржи» (SXPUSDT на демо Binance 05.11.2026: состояние
`TRADING`, последняя и единственная за окно сделка 19.10.2026, на боевом адресе символа уже нет).
Свежая последняя сделка или отметка раньше сделки — по-прежнему расхождение. Время сделки обязано
быть миллисекундами больше нуля: секунды, ноль или отрицательное число — расхождение, а не «данные
биржи». Если биржа на запрос сделок отдала пустой список, это «данные биржи: сверить не с чем»
только при согласованных собственных полях тикера — конец окна суток в миллисекундах и не в
будущем (начало окна в общий тикер библиотеки не попадает, поэтому его сверка не делается);
иначе расхождение. Со сделками сверяются только первые 10 таких инструментов, остальные из этой
группы сразу идут расхождением с пометкой, что не сверялись. Отметка в будущем — расхождение
всегда, торгуемый инструмент или нет. Признак торгуемости берётся из списка инструментов: если он
к моменту проверки тикеров ещё не прочитан (запуск с `--only=Тикеры`), проверка читает его сама
через общий для прогона запас контекста. Прежний порог правдоподобия («не больше 1000 %») сваливал в одну кучу настоящую
беду — величина не число — и подлинные числа демо-стенда: учебная пара OKX, чья цена ушла со ста
до 5·10¹⁴, даёт полтриллиона процентов и при этом арифметически безупречна. Правило единое на все
три биржи, ветки по бирже в нём нет.

### Код выхода

| Код | Когда |
|---|---|
| `0` | у всех бирж остались только `подтв.`, `не прим.` и `пропуск` |
| `1` | хоть у одной биржи есть `расх.`, `неполн.` или `неудача`; либо вышел общий срок прогона |

Перед кодом печатается список того, что за человеком: биржа, статус и название обещания. `пропуск`
код не поднимает — обещание не выполнялось сознательно (нет ключей счёта или не задан
`--allow-orders`), и обещать по нему нечего; ровно поэтому прогон без ключей завершается нулём.
`не прим.` его тоже не поднимает: краснота, за которой нет ничего чинимого, обесценивает сам код
выхода. `неудача` поднимает: недоступный ключ (например, `10010` у Bybit) — это прогон, который не
доказал ничего, и внешняя обвязка обязана это видеть.

### Безопасность

- **Ключи не печатаются никогда.** Всё, что уходит в вывод (включая журнал библиотеки), проходит
  через замену: если в тексте встретится ключ, секрет или кодовая фраза, на их месте окажется
  «скрыто».
- **По умолчанию только чтение.** Заявки ставятся только с `--allow-orders`. Обещание 14 —
  минимальный объём по фильтрам инструмента по ETHUSDT, лимитная цена ВДВОЕ ниже рынка (сработать не может).
  Заявок по BTCUSDT прогон не ставит нигде. Обещания 15 и 16 — рыночная покупка наименьшего объёма
  ETHUSDT и закрывающая продажа своим объёмом. Обещание 16 на Binance проходит ETHUSDT в общей и в
  изолированной марже и возвращает прежний режим; на Bybit режим маржи (он общий на весь счёт) не
  переключает никогда. Обещание 17 меняет плечо ETHUSDT на соседнее значение и возвращает прежнее,
  на Bybit ещё переключает в двусторонний режим ТОЛЬКО ETHUSDT и возвращает обратно. Наименьший
  объём считается от последней цены, прочитанной заново прямо перед пробой, а не от тикеров начала
  прогона, и округляется вверх до шага объёма самой библиотекой.
- **Перед пробой с заявками ETHUSDT обязан быть свободен.** Обещания 14–17 сначала читают позицию и
  открытые заявки по ETHUSDT: если есть позиция (любой стороны) или заявка, у которой клиентский
  номер не начинается с метки этого запуска, проба ничего не ставит и настроек не меняет, а
  печатает «не прим.» с причиной.
- **Позиция закрывается только своим объёмом.** У прогона по каждой бирже есть реестр своей
  позиции по ETHUSDT: каждая рыночная заявка записывает в него исполненный объём (прочитанный по
  самой заявке; если исход постановки неизвестен — по клиентскому номеру). Закрытие идёт ровно
  этим объёмом и с признаком «только уменьшение» (в двустороннем режиме — по своей стороне), а не
  объёмом позиции счёта. Если после закрытия своего объёма позиция на счёте не пуста — это
  расхождение «появилась чужая позиция», и проба её не трогает; изолированная маржа на Binance
  после этого режим маржи дальше не переключает. Неудачное закрытие оставляет объём в реестре, и
  его снова пытается закрыть уборка.
- **Уборка тройная и только своё.** Каждое обещание снимает поставленное и закрывает свой объём в
  своём `finally`; в конце прогона биржи идёт сквозная уборка; при выходе общего срока — уборка
  перед выходом. Сквозная уборка и уборка по общему сроку снимают заявки с меткой этого запуска
  (`elc…`) отдельно по BTCUSDT и по ETHUSDT — отказ по одному символу не прерывает уборку по
  другому — и закрывают свой объём из реестра. **Чужие позиции и заявки не трогаются вовсе.**
- **Срок обещания не бросает пробу на ходу.** Когда срок вышел, раннер подаёт пробе сигнал
  остановки — проба перестаёт ставить заявки и менять настройки и идёт в свою уборку — и ждёт её
  завершения до 90 с. Не дождался — следующие пробы с заявками не запускаются, пока она не
  закончит: им ставится «неполн.» с названием незавершённой пробы.
- **Тайм-ауты.** Обычное обещание — 60 с, список инструментов — 300 с, тикеры — 480 с (180 с на
  тикеры плюс 300 с на список инструментов, если проверка читает его сама), ступени плеча — 120 с,
  потоки — 240 с, оборот заявки и сводка исполнений — по 180 с, режим маржи и изолированная
  маржа — 240 с, плечо с направлением — 120 с. Превышение даёт «неудача» с текстом, а не зависание; рядом со статусом печатается,
  сколько на самом деле ждали, а если биржа в это время держала адрес закрытым по частоте запросов —
  об этом говорится отдельной фразой со сроком снятия. Список инструментов получил втрое больший
  срок потому, что демо-вход спота Binance отдаёт его порциями и укладывается за 150–180 с и очень неровно;
  срок обязан быть длиннее внутреннего срока запроса библиотеки (30 с) со всеми её повторами, иначе
  вместо причины отказа биржи в вывод попадает наша собственная нетерпеливость.
- **Общий срок прогона — 35 минут.** По нему текущей пробе подаётся сигнал остановки, выполняется
  уборка перед выходом (свои заявки по метке и свой объём по реестру, не дольше 120 с), печатается
  ИТОГОВАЯ ТАБЛИЦА с тем, что успели (до чего не дошло — прочерк), и процесс завершается КОДОМ 1. Без этого прогон мог оборваться посреди
  обещания с кодом 0 и без таблицы: все паузы внутри библиотеки (повтор запроса, ожидание снятия
  запрета биржи) заведены таймерами, не удерживающими процесс живым, и стоило единственной такой
  паузе остаться в одиночестве, как очередь событий пустела и Node завершался успехом. По той же
  причине собственный срок обещания процесс УДЕРЖИВАЕТ и снимается сразу после того, как обещание
  отработало.
- После итоговой таблицы скрипт ждёт естественного завершения процесса: если через 5 с он всё ещё
  жив, печатается предупреждение, что `close()` оставил таймеры или сокеты.

### Известные особенности демо-счетов

- **Bybit**: если демо-ключ привязан к списку адресов, вызов с машины вне списка отвечает
  `10010 Unmatched IP`, и обещания получают «неудача» с этим кодом — это не расхождение договора,
  а недоступный ключ; снимается только в кабинете биржи. В демо-режиме библиотека шлёт ВСЕ
  запросы, включая рыночные чтения (инструменты, тикеры, свечи, стакан, сделки), на демо-адрес
  `api-demo.bybit.com` и подписывает их ключом; без ключа идёт только чтение свечей цены
  маркировки. Поэтому цены в пробах с заявками — цены того же демо-стенда, где исполняются заявки.
  Задевает ли отказ `10010` подписанные рыночные чтения, живьём не проверялось. Ключей не требуют
  только публичные потоки: они идут на боевой адрес `stream.bybit.com`. Демо-счёт Bybit НЕ обслуживает ручку ставок комиссии (`/v5/account/fee-rate` нет в
  перечне ручек демо-торговли, живой ответ — код `10001` с пустым текстом): обещание 10 у Bybit
  печатается «не применимо». Сводных полей счёта (капитал, свободные) демо-ответ не несёт, а
  долларовая оценка монеты у Bybit — её капитал с плавающим итогом открытых позиций, поэтому сумма
  оценок сверяется с капиталом счёта, а не с кошельком; без капитала сверка не делается.
- **Binance**: спотовые обещания идут на демо-адрес спота; если он для ключа недоступен, обещания
  спота честно помечаются «неудача» с ответом биржи. Демо-вход спота вдобавок ОЧЕНЬ медленный на
  тяжёлых ответах: список инструментов (3698 записей) приходит за 150–180 с, а иногда не приходит и за 180 с, тогда как боевой вход
  отдаёт его же за 11 с (замер 10.09.2026). Это свойство демо-стенда, а не библиотеки и не предела
  частоты запросов: расход веса на этот момент — единицы из 2400.
  Стакан BTCUSDT демо-стенда фьючерсов держит на верхних уровнях сотни монет: 15 чтений
  05.11.2026 — лучшая покупка от 0.98 до 595.5 BTC (около 47 млн USDT), на продаже до 1216.5 BTC;
  в прогоне того же дня — 652.4241 BTC по 79605.3, то есть 51.9 млн USDT. Боевой стакан в те же
  минуты — от 0.12 до 17.7 BTC на верхнем уровне. Поэтому обещание 6 больше не ставит потолок
  номинала верхнего уровня (было 50 млн): он срабатывал на подлинной крупной заявке демо-стенда и
  при этом пропускал количество в контрактах у мелкого верхнего уровня.
- **OKX**: демо-счёт может держать ОТКРЫТУЮ позицию, заведённую вручную ради других проверок.
  Скрипт её не закрывает и не считает мусором.

## `okx-live-probe` — десять утверждений про OKX

Десять утверждений про OKX нельзя доказать чтением документации — только ответом самой биржи.
Скрипт прогоняет каждое утверждение по демо-ключам и печатает для него «подтверждено /
расходится / неполная / не удалось / не выполнена» вместе с ДОСЛОВНЫМ ответом биржи, чтобы
решение по каждому утверждению принималось по факту, а не по догадке.

### Ключи демо-счёта OKX

По документации OKX демо-ключ заводится так (названия пунктов у биржи меняются, ориентируйтесь по
смыслу):

1. Войти на okx.com обычным счётом.
2. Перейти в раздел демо-торговли («Demo trading» / «Демо-торговля»).
3. Внутри демо-счёта открыть управление ключами и создать ключ **именно для демо-торговли**.
4. При создании задать кодовую фразу (passphrase) — её придумывает владелец, восстановить её
   потом нельзя. Права: достаточно чтения; «торговля» нужна только для запуска с `--allow-orders`.
5. Ключ демо-счёта работает исключительно с заголовком `x-simulated-trading: 1`, который
   библиотека ставит сама при `isDemoMode`. Боевой ключ на демо-адресах не работает и наоборот.

### Куда положить ключи

Рядом с `package.json` создать файл `.env` по образцу `.env.example` (сам `.env` уже в
`.gitignore`, в хранилище он не попадёт):

```
OKX_API_KEY=...
OKX_SECRET=...
OKX_PASSPHRASE=...
```

Все живые проверки ходят только на демо-счета; боевого режима у скриптов нет.

Имена переменных — соглашение этой библиотеки и только оно: `OKX_API_KEY`, `OKX_SECRET`,
`OKX_PASSPHRASE`. Других наборов имён проба не понимает; полный образец, включая ключи Binance и
Bybit, — в `.env.example`.

### Запуск

Файл `.env` читает собственный разборщик `scripts/live-support/liveEnvFile.ts` (пакета `dotenv` в
зависимостях нет и ставить его нельзя), переменная оболочки сильнее файла. Поэтому запуск — одна
команда, без `source`:

```bash
yarn okx:probe
```

Без ключей скрипт запускается тоже — и честно печатает, каких переменных не хватает, а в итоговой
таблице все десять проб помечает «не выполнена». Это самый быстрый способ убедиться, что скрипт
собирается и стартует:

```bash
yarn okx:probe
```

#### Ключи запуска

| Ключ | Что делает |
|------|-----------|
| `--allow-orders` | Разрешает пробам СТАВИТЬ заявки. Без него скрипт только читает. |
| `--inst-id=BTC-USDT-SWAP` | Инструмент для всех проб. По умолчанию `BTC-USDT-SWAP`. |
| `--only=<кусок текста>` | Прогнать только те пробы, в чьём утверждении встречается этот текст. |
| `--verbose` | Печатать ещё и журнал библиотеки (потоки, повторы, отказы). |

Пример: `yarn okx:probe --allow-orders --verbose`

### Что делает каждая проба

| № | Утверждение | Нужен `--allow-orders` |
|---|-------------|------------------------|
| 1 | Торговый канал (WebSocket) принимает строковый `instId`, а не числовой `instIdCode` | **да** |
| 2 | `groupId` инструмента совпадает с `groupId` внутри `feeGroup` ответа о комиссии | нет |
| 3 | В `history-candles` параметр `after` исключает свечу с такой же отметкой времени | нет |
| 4 | Ответ по балансу заполняет `availEq`, `adjEq`, `imr`, `ordFroz`, `upl` | нет |
| 5 | Условные заявки приходят каналом `orders-algo` на деловом адресе | подписка — нет, приход события — да |
| 6 | Подтип 174 — приход фандинга, 173 — расход, сумма лежит в `pnl` | нет |
| 7 | Строки многострочного кадра `candle1m` идут от старой свечи к новой | нет (многострочный кадр OKX шлёт при догоне после разрыва — если за минуту ожидания он не пришёл, проба «неполная») |
| 8 | Постраничный обход заявок (`after = ordId`) идёт от новой записи к старой | нет (без ключа читается история заявок вместо открытых) |
| 9 | Запятая в подписанной строке запроса принимается биржей | нет |
| 10 | Маржа под висящей заявкой входит в `details[].imr` на уровне монеты, а не только в `ordFrozen` | **да** (без ключа проба «неполная»: без своей заявки вопрос не закрыть) |

Пробы, которым нужен `--allow-orders`, без него помечаются «не выполнена» — они НЕ считаются
неудачей и не путаются с настоящим отказом биржи. Отдельный статус «неполная» означает третье:
проба отработала и напечатала сырые ответы, но условий для вывода не сложилось (биржа не прислала
нужного кадра; на счёте нечего сравнивать). Это тоже не отказ биржи.

### Безопасность

- **Ключи не печатаются никогда.** Всё, что уходит в вывод (включая журнал библиотеки), проходит
  через замену: если в тексте встретится ключ, секрет или кодовая фраза, на их месте окажется
  «скрыто».
- **По умолчанию только чтение.** Заявки ставятся исключительно с `--allow-orders`: минимальный
  объём инструмента, лимитная цена вдвое ниже рынка (сработать не может), условная заявка с
  порогом вдвое ниже рынка.
- **Уборка двойная.** Каждая проба снимает поставленное в своём `finally`; в конце запуска с
  `--allow-orders` идёт сквозная уборка — снимается всё, у чего клиентский номер начинается с
  метки этого запуска (`okxprobe…`). Чужие заявки на счёте проба не трогает: отбор идёт строго по
  этой метке.
- **Тайм-ауты.** Обычная проба — 30 с. Проба 5 — 60 с (20 с на подписку, 25 с на приход
  события). Проба 7 ждёт многострочный кадр до 60 с, поверх неё сторож на 70 с. Превышение даёт
  «не удалось» с текстом, а не зависание.

## Устройство и проверка обоих скриптов

Общее у двух скриптов лежит в `scripts/live-support/` и подключается обоими, а не копируется:
замена ключей в печати и вывод (`liveOutput`), разбор отказа биржи (`liveError`), журнал
библиотеки с той же заменой (`liveLogger`), чтение ключей запуска и переменных окружения
(`liveCommandLine`), ожидание условия (`liveWait`). Там же `liveOrder` — наименьший объём,
рыночные заявки и реестр своей позиции; им пользуется только `exchange-live-check`.

`scripts/exchange-live-check.ts` — точка входа проверки договора, по файлу на обещание в
`scripts/exchange-live-check/`. Она ходит ТОЛЬКО через публичный вход `ExchangeClient` (и фабрику
`Exchange`): смысл проверки в том, что обещано наружу, а не в том, как оно устроено внутри.
Потоковое обещание поднимает СВОЙ экземпляр `Exchange`, чтобы его `close()` не гасил соединения,
нужные остальным обещаниям.

`scripts/okx-live-probe.ts` — точка входа пробы OKX, по файлу на пробу в `scripts/okx-live-probe/`.
Скрипт берёт публичный вход библиотеки там, где он подходит, но большинству проб нужен ДОСЛОВНЫЙ
ответ биржи, который публичный слой как раз и нормализует; поэтому используются внутренние
`OkxHttpClient`, `OkxTradeStream`, `OkxPrivateStream` и транспорт `ReliableWebSocket`. Отдельно
отмечу пробу 1: `createOrderWebSocket` при неготовом торговом канале молча уходит на REST, и её
успех ничего не сказал бы про канал, — поэтому проба обращается к торговому каналу напрямую.

```bash
yarn tsc -p scripts/tsconfig.json --noEmit   # проверка типов скрипта
yarn lint                                    # линт библиотеки, тестов И скриптов
```

`yarn lint` охватывает скрипты: каталог `scripts/` разбирается наравне с `src/` и `test/`. Печать
в терминал (`console.log`) для `scripts/**` разрешена отдельным исключением — так же, как она
разрешена для тестов.
