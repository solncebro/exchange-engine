# Exchange Layer — OKX: поток счёта и конкретные классы

Часть `exchange-layer-okx.md` (см. индекс там). Поток событий счёта, соединения и завершение, `OkxSwap` и `OkxSpot`.

## Поток событий счёта — два соединения

`connectUserDataStream(handler)` поднимает ДВА `OkxPrivateStream`:
1. личный вход (`privateWebSocketUrl`) — темы `orders` (по `instType`), `positions` (только для контракта) и `account`;
2. деловой вход (`businessWebSocketUrl`) — тема `orders-algo`. Без второго соединения срабатывание стопа осталось бы незамеченным.

Повторный вызов при уже поднятом потоке — предупреждение и выход. `disconnectUserDataStream()` закрывает оба и обнуляет поля. `isUserDataStreamConnected()` отвечает «да», только когда живы ОБА.

Разбор: `orders` → `handler.onOrderUpdate(buildOkxOrderUpdateEvent(...))`; `positions` → `handler.onPositionUpdate(buildOkxPositionUpdateEvent(...))`, записи не-`SWAP` пропускаются; сторона события говорит на словаре соседей (`'Buy'`/`'Sell'`/`''`, как у `BybitBaseClient` и `BinanceBaseClient`), а не сырым `net`/`long`/`short` OKX, и берётся из направления (`resolveOkxPositionDirection`), а не из `posSide`: в одностороннем режиме `posSide` ВСЕГДА `net`, и направление живёт только в знаке `pos`, тогда как `size` отдаётся по модулю — как у обеих соседних бирж; `account` → `handler.onBalanceUpdate(...)`, если обработчик задан; `orders-algo` → `buildOkxAlgoOrderUpdateEvent` плюс пометка номера в реестре как условного. Каждое событие выполняется через `runUserDataHandler` — ошибка в обработчике одного события не обрывает разбор остальных. **Инструмент разбирается ДО вызова обработчика** (`takeOkxInstrumentOrWarn`, отдаёт общее имя и множитель контракта одним разбором; `takeOkxContractValueOrWarn` — тонкая обёртка над ним): инструмент не из карты (свежий листинг после последней загрузки) даёт предупреждение С ЕГО ОБОЗНАЧЕНИЕМ и пропуск события, а не безымянную строку «обработчик отказал» уровня ошибки — вызывающий иначе не узнавал, по какому инструменту он перестал получать события. Обозначения в записи: `the order stream`, `the position stream`, `the conditional order stream`.

## Соединения и завершение

`getWebSocketConnectionInfoList()` — публичные соединения плюс, если есть, торговое, личное и деловое. `close()` отключает торговый канал, зовёт `disconnectUserDataStream()` (как Binance и Bybit — раньше тело дублировалось, и строка журнала «поток счёта отключён» не писалась) и закрывает публичный поток.

## Конкретные классы — OKX

## OkxSwap
- `marketLabel = 'swap'`, `instType = 'SWAP'`
- `marginModeBySymbol` — память клиента о режиме маржи; `resolveTradeMode(symbol)` (async) отдаёт `'cross'`/`'isolated'` через `ensureMarginMode`
- `ensureMarginMode(symbol)` — при отсутствии записи в памяти спрашивает биржу ОДИН раз НА СЧЁТ: позиции читаются одним запросом по всем инструментам (`readMarginModesFromOpenPositions` → `/api/v5/account/positions` БЕЗ `instId`, поле `mgnMode`), и память заполняется сразу по всем инструментам с открытой позицией; признак `hasReadMarginModes` держит последующие символы в памяти. Раньше после перезапуска процесса память была пуста и КАЖДАЯ заявка уходила с `tdMode: 'cross'` по позиции, которую биржа держит изолированной, — биржа отвергала её, включая защитную; а чтение по одному инструменту давало пачке из 20 символов 20 ПОСЛЕДОВАТЕЛЬНЫХ запросов до отправки первой заявки (заявки пачки собираются по одной), при пределе входа 10 запросов за 2 секунды. Параллельные вызовы делят один запрос (`marginModeLookup`); инструмент без открытой позиции считается общим (`cross`); отказ чтения НЕ запоминается — предупреждение в журнал с именем спросившего символа, прежнее умолчание, следующая заявка спросит заново; явный `setMarginMode` всегда сильнее прочитанного (снимок не трогает уже занятые записи); инструмент, обозначение которого не разбирается, пропускается с предупреждением и не роняет чтение остальных. **Оговорка:** память стала счётной, поэтому изолированная позиция, открытая руками ПОСЛЕ снимка по инструменту, которого клиент ещё не касался, замечена не будет. Ручка `/api/v5/account/leverage-info` для этого непригодна — она принимает `mgnMode` вводом и лишь возвращает его эхом, то есть режима не называет
- `setMarginMode(marginMode, symbol)` — запоминает выбор, сверяет его с режимом счёта (`warnIfIsolatedMarginIsUnavailable`: изолированной маржи нет при `acctLv ∈ OKX_ISOLATED_MARGIN_UNAVAILABLE_ACCOUNT_LEVEL_LIST` = 3/4, «isolated is not available in multi-currency margin mode and portfolio margin mode» — иначе биржа отвергала бы КАЖДУЮ последующую заявку, а сам выбор прошёл бы молча) и проверяет открытые позиции по инструменту: если позиция открыта в ДРУГОМ режиме, пишет предупреждение (сменить режим под открытой позицией OKX не даёт, а тихий отказ выглядел бы как удача). Сбой чтения режима счёта или позиций не срывает метод — предупреждение и выход
- `fetchPositionMode()` → `ensureAccountConfig()`: `long_short_mode → Hedge`, `net_mode → OneWay`, иначе `undefined`
- `setPositionMode(mode)` — если на счёте уже нужный режим, ничего не шлёт; иначе `/api/v5/account/set-position-mode` и сброс кеша конфигурации
- `setLeverage(leverage, symbol)` → `SetLeverageResult`. В режиме «лонг и шорт» с изолированной маржой плечо ставится ДВУМЯ запросами (`setOkxHedgeIsolatedLeverage`), и **оба уходят всегда** — даже если первый отказал. Опасен не отказ первого (тогда на бирже ничего не изменилось), а отказ ВТОРОГО: одна сторона уже с новым плечом, другая со старым. Отказ любого из них выходит наружу `ExchangeError('OKX_LEVERAGE_SIDES_DIVERGED')`, и текст называет, какая сторона отвергнута, а какая уже изменена. `confirmedLeverage` (`resolveOkxConfirmedLeverage`) заполняется, только если ВСЕ ответы назвали одно и то же конечное число `≥ 1`, иначе `null`
- `fetchPosition(symbol)` — первая запись ответа; пусто → `Position not found for …`
- `fetchPositionSnapshot(symbol, positionIdx?)` — без `positionIdx` при инструменте в режиме «лонг и шорт» бросает ошибку (вызывающий обязан назвать сторону явно); допустимые значения `0` (нетто), `1` (лонг), `2` (шорт), сверяются через `OKX_POSITION_IDX`
- `fetchPositionList(symbol)` / `fetchAllPositions()` — вторая пропускает нулевые позиции и записи, чей `instId` не разбирается или не входит в загруженную карту (предупреждение в журнал), поэтому инверсный контракт на счёте её не рушит
- `fetchOpenConditionalOrders(settleCoin)` — отбор по валюте расчёта; условная заявка на инструменте, которого нет в загруженной карте (свежий листинг, снятый с торгов), выпадает из ответа С ПРЕДУПРЕЖДЕНИЕМ, называющим номер заявки и обозначение инструмента, — молчаливое выпадение выглядело бы как «стопов нет»
- `fetchFundingRateHistory(symbol, options?)` — окно сдвигается: `after = endTime + 1`, `before = startTime − 1` (`after` у OKX строго раньше отметки); лимит клампится к `OKX_FUNDING_RATE_HISTORY_LIMIT` (400)
- `fetchFundingInfo(symbol?)` → `/api/v5/public/funding-rate`; без символа запрашивается `'ANY'` и список фильтруется по загруженной карте инструментов
- `fetchMarkPrice(symbol?)` — ТРИ запроса параллельно (цена маркировки, ставка фандинга и индекс `/api/v5/market/index-tickers`), сводятся в `MarkPrice`; без символа список фильтруется по карте. Индекс адресуется обозначением БЕЗ хвоста `-SWAP` (`toOkxIndexInstId`), а без символа — по каждой валюте расчёта; отказ ручки индекса не срывает метод (предупреждение, `indexPrice` остаётся пустым)
- `fetchOpenInterest(symbol)` — пустой ответ → `OKX_OPEN_INTEREST_EMPTY`; символ проставляется поверх нормализованной записи
- `fetchClosedPnl(symbol?, options?)` → `/api/v5/account/positions-history` через `fetchAllPositionsHistory`, с тем же сдвигом окна, что у истории фандинга. Читается постранично (курсор — отметка закрытия `uTime`; полная страница на сотне записей раньше молча обрезала ответ). **`options.limit` — сколько строк ИТОГА вернуть**, а не размер страницы; умолчание — `OKX_POSITIONS_HISTORY_PAGE_LIMIT` (100). Гранулярность иная, чем у соседей, и строка НАКОПИТЕЛЬНАЯ: одна запись на всю жизнь позиции, ОБНОВЛЯЕМАЯ при каждом частичном закрытии («Position's cumulative closed volume», «Accumulated fee», «It is the latest type if there are several types for the same position»; страницы адресуются `uTime` — временем обновления). Одна и та же позиция вернётся и за понедельник (итог 10), и за вторник (итог уже 25), поэтому **складывать итоги OKX по окнам нельзя** — выйдет задвоение (35 вместо 25); берут последнее значение по номеру позиции. Строка может относиться к ещё ОТКРЫТОЙ позиции (частичное закрытие), то есть итог не окончателен. В `ClosedPnl.orderId` лежит номер позиции (`posId`) — своего номера заявки у записи биржи нет, сверять итоги с заявками по номеру на OKX не получится (у Binance строка на закрывающую заявку, у Bybit — на запись закрытия). Библиотека это НЕ выравнивает: так устроен ответ биржи, знать должен потребитель (см. JSDoc `ClosedPnl` и `OkxSwap.fetchClosedPnl`)

## OkxSpot
- `marketLabel = 'spot'`, `instType = 'SPOT'`
- `resolveTradeMode()` (async) → `'cash'`: у спота нет режимов маржи, заявка расплачивается наличным остатком счёта
- Всё остальное — из `OkxBaseClient`; фьючерсные методы наследуют отказ `Not supported for spot market` из `BaseExchangeClient` (позиции, плечо, режимы, фандинг, цена маркировки, открытый интерес, итоги закрытия)
