## [Unreleased] — Темп исходящих команд: защита от каскада переподписок

Разбор аварии 08.08.2026 (kliner, боевой сервер). В 14:04:57 биржа тихо перестала отдавать
данные по 120 потокам на **живом** соединении, сторож приложения в ту же секунду отправил 120
починок — по две команды на поток, то есть до 240 команд за секунду при лимите Binance
10 команд в секунду на соединение. Биржа закрыла соединение кодом 1008, данные пропали, сторож
увидел ещё больше устаревших символов и ударил сильнее. Круг длился около трёх часов и не
разрывался перезапуском приложения. Замеры из журнала: 120, 166 и 50 команд за одну секунду.

### Added

- **Очередь исходящих команд на каждое соединение** (`OutboundCommandQueue`, темп по умолчанию
  8 команд в секунду при лимите биржи 10). Через неё теперь идут все отправки: начальная
  подписка, точечные подписка и отписка, починка потоков. Очередь сбрасывается при
  пересоздании соединения — команда для сокета, которого уже нет, бесполезна, а новый сокет
  и так подписывается заново при открытии. (`src/ws/OutboundCommandQueue.ts`,
  `src/ws/OutboundCommandQueue.types.ts`, `src/ws/streamCommandRateLimit.ts`)
- **Пакетная переподписка** — `resubscribeKlineList(argsList)` у клиента биржи и
  `resubscribeStreamList` у потока. Позволяет вызывающему отдать весь список разом, вместо
  вызова на каждый символ. (`src/types/exchange.ts`, `src/types/stream.ts`,
  `src/exchanges/BaseExchangeClient.ts`)
- **Темп и длина очереди видны снаружи** — `pendingCommandCount` и `maxCommandsPerSecond` в
  сведениях о соединении, попадают в диагностические снимки потребителя. (`src/types/common.ts`)
- **Дробление kline-потоков Binance-фьючерсов по соединениям через конфиг.** Настройка
  `publicStreamConnectionPacking.maxTopicsPerConnection` из `ExchangeConfig` (раньше её читал
  только Bybit) теперь пробрасывается в `BinanceFuturesPublicStream` как потолок потоков на
  соединение: группа таймфрейма, превысившая потолок, раскладывается на несколько соединений
  («осколков»). Механизм раскладки в потоке существовал и был покрыт тестами, но настройка
  снаружи не доходила — всегда действовал зашитый потолок 900, и все ~523 потока таймфрейма
  ехали одним соединением. Каждый осколок получает уникальную метку (`interval-1m`,
  `interval-1m #2`, …) — иначе журнал и диагностика не различали бы их; починка потоков
  (`resubscribeStreamList`) адресуется тому осколку, которому принадлежит поток, соседние не
  трогаются; порог каскадного пересоздания (50 потоков) действует на каждый осколок отдельно.
  Дефолт не изменился (без настройки — прежнее одно соединение на таймфрейм). Основание —
  параллельный опыт на боевом сервере 11.08.2026: соединение на 523 потока в пик (13:00–16:00
  UTC) биржа переставала кормить (в 14:37 разом умерло 471 из 523 потоков, включая биткоин) и
  рвала сбросом без кода закрытия, а соседнее соединение на 30 потоков с той же машины по тому
  же маршруту Амстердам→Токио прошло весь шторм без единой дыры и ошибки.
  (`src/exchanges/BinanceFutures.ts`, `src/ws/BinanceFuturesPublicStream.ts`,
  `src/types/common.ts`)

### Fixed

- **Починка потоков больше не бьёт залпом.** `resubscribeStreamByName` копит потоки в окне
  250 мс и разбирает их одним решением, а не двумя мгновенными командами на каждый поток.
  Защита работает независимо от вызывающего: и уже развёрнутые версии приложений, и сторож
  внутри `trade-engine` становятся безопасными без единой правки на их стороне.
  (`src/ws/BinanceFuturesPublicStream.ts`)
- **Массовая пропажа данных чинится одним пересозданием соединения.** Если разом затронуто
  50 потоков и больше, поштучный ремонт бессмысленен вдвойне: он и стоит вдвое дороже полной
  переподписки, и не лечит причину — на соединении, которое биржа перестала обслуживать,
  снятие и повторная подписка ничего не меняют. Помогает только новый сокет.
  То же правило добавлено для Bybit по числу тем на соединении. (`src/ws/BinanceFuturesPublicStream.ts`,
  `src/ws/BybitPublicStream.ts`)
- **Закрытие по нарушению правил (код 1008) больше не игнорируется.** Раньше обработчик
  закрытия у публичного потока Binance вообще не был подключён. Теперь такое закрытие пишется
  в журнал, чистит очередь команд и на минуту запрещает точечную починку этого соединения —
  остаётся только пересоздание. (`src/ws/BinanceFuturesPublicStream.ts`)
- **Ожидание готовности соединений честное.** `awaitConnectionsReady` сперва сбрасывает
  отложенные склейки и ждёт опустошения очередей — иначе вызывающий возвращался раньше, чем
  работа вообще была запланирована. (`src/ws/BinanceFuturesPublicStream.ts`)
- **Ожидаемый отказ Binance «Order does not exist» больше не пишется как ошибка.** Заявка может
  принадлежать обычной книге ИЛИ службе условных заявок, а спросить «чья она» биржа не даёт —
  поэтому чтение спрашивает обе службы разом и берёт ту, что узнала номер. Вторая по замыслу
  всегда отвечает −2013, и общий клиент запросов писал этот ответ уровнем ошибки: на боевом
  сервере rubber — 74 пугающие строки за сутки рядом с успешными операциями, против одной
  настоящей ошибки. Теперь такой ответ идёт уровнем info с кодом и текстом. Меняется ТОЛЬКО
  уровень записи: объект ошибки вызывающему отдаётся прежним (`[код] сообщение`), потому что
  по этому тексту вызывающие опознают «заявки уже нет» и считают отмену выполненной, а тот,
  кому пропажа заявки действительно важна, сообщает о ней сам. Существующий список безобидных
  ответов для этого не годился: он заодно лишает ошибку текста. (`src/http/BaseHttpClient.ts`)

### Notes

- Требует `@solncebro/websocket-engine` 0.5.0 — там появился жёсткий предохранитель темпа
  (9 команд в секунду, выше темпа очереди и ниже лимита биржи) и чтение ответа биржи при
  обрыве. Предохранитель в норме не срабатывает: если сработал — это ошибка, и она громкая.
- Параметр `pauseBetweenSubscribeBatchesMs` больше не влияет ни на что: темп задаёт очередь.
  Он оставлен в аргументах ради совместимости и игнорируется.

## [0.20.0] - 2026-08-08 — Равенство бирж, 9 этапов: последние проверки и доводки

Большой выпуск серии аудита расхождений Binance ↔ Bybit. Девять этапов фиксации мест,
где потребитель просит защиту и молча её не получает, либо получает, но другую на каждой
бирже. Требование владельца: за одним интерфейсом обе биржи обязаны вести себя одинаково.

### Added

- **Скользящий стоп на Bybit работает.** У Bybit это не заявка, а свойство позиции
  (`/v5/position/trading-stop`, отступ — расстояние в цене, `"0"` снимает), поэтому раньше
  такой запрос молча собирался в неподвижный рыночный стоп по первоначальной цене — всё
  движение отдавалось обратно. Теперь `createOrderWebSocket` ставит скольжение, `cancelOrder`
  снимает, `getOrder` читает живое состояние с позиции. Номер выводится из адреса позиции, а
  не запоминается: у одной позиции скольжение ровно одно, поэтому такой номер переживает
  перезапуск процесса — память бы опустела, и снять поставленное до перезапуска стало бы
  нечем. Отступ в процентах переводится в расстояние от цены вооружения (не названа — от
  текущей цены маркировки) и кладётся на сетку цены символа.
  (`src/exchanges/BybitLinear.ts`, `src/exchanges/bybitTrailingStopId.ts`)
- **Спот Bybit отказывает громко.** Скольжения там нет вовсе, и молчаливая подмена рыночным
  стопом хуже отказа. (`src/exchanges/BybitBaseClient.ts`)
- **`fetchClosedPnl` на фьючерсах Binance.** Собирается из `/fapi/v1/userTrades` (входа в
  клиенте не было вовсе): одна запись на закрывающую заявку, средневзвешенная цена выхода,
  итог. Символ необязателен — без него читается весь счёт, как и у соседней биржи.
  (`src/exchanges/BinanceFutures.ts`, `src/normalizers/binanceNormalizer.ts`,
  `src/http/BinanceFuturesHttpClient.ts`)
- **Фильтр журнала начислений понимает три намерения** вместо одного: ставка финансирования,
  реализованный итог, комиссия. Плюс символ. У Binance фильтрует сама биржа, у Bybit —
  отбор на месте, потому что его вход символа не принимает. (`src/types/exchange.ts`,
  `src/constants/mappings.ts`, `src/exchanges/BybitBaseClient.ts`)
- **Поток стакана у фьючерсов Binance написан.** Его не было вовсе — не потому, что биржа
  его не даёт, а потому что работа была не закончена. Подписка, отписка и переподписка
  встроены в ту же машинерию соединений, что и остальные потоки (отдельная группа соединений,
  динамическая подписка, переподписка после обрыва). Кадр приходит в той же форме, что у
  соседней биржи: склейку делает потребитель, а не слой связи.
  (`src/ws/BinanceFuturesPublicStream.ts`, `src/normalizers/binanceNormalizer.ts`)
- **Обновление средств приходит и на фьючерсах.** Раньше оно было только на споте Binance.
  Binance-фьючерсы отдают его из того же события счёта, Bybit — по теме кошелька, на которую
  клиент теперь подписан. У Bybit намеренно заполняется только остаток кошелька: «доступное
  к выводу» на едином счёте означает не то же, что «свободное» на споте, и подменять одно
  другим — тихая ложь. (`src/exchanges/BinanceBaseClient.ts`, `src/exchanges/BybitBaseClient.ts`)
- **Сквозной тест равенства** (`test/exchanges/exchangeParity.test.ts`): ОДИН список
  ожиданий, прогоняемый по обеим биржам сразу — возможности, которых у рынка нет, отказывают
  громко и одинаково; единицы измерения общие; предел частоты называет свой источник;
  защитная заявка узнаётся везде. Смысл не в повторении проверок каждой биржи, а в том,
  чтобы РАСХОЖДЕНИЕ между ними падало здесь: до сих пор такие вещи находил только сплошной
  аудит — спустя месяцы и после денежных потерь. Каждое новое общее обещание добавляется сюда.

### Changed

- **BREAKING: `trailingDelta` убран из общего контракта.** Он выражал отступ в сотых долях
  процента — собственной единице спота Binance — и был второй правдой рядом с `callbackRate`.
  Отступ скольжения теперь везде задаётся ТОЛЬКО `callbackRate`, в процентах; перевод в
  единицу биржи происходит на границе запроса и наружу не выходит.
  (`src/types/exchange.ts`, `src/exchanges/BinanceBaseClient.ts`, `src/constants/binance.ts`)
- **BREAKING: `createBatchOrders` возвращает исходы, а не заявки.** Было `Order[]`, стало
  `CreateBatchOrdersResult` — по записи на каждую входную заявку: сама заявка (или `null`),
  признак успеха, код и текст отказа биржи. Форма повторяет ту, что уже была у пакетной
  отмены и изменения, — третьей выдумывать не стали. (`src/types/exchange.ts`)
- **BREAKING: цена маркировки, плечо и цена ликвидации в событии позиции стали
  `number | null`.** У Binance их в событии НЕТ вовсе (образец полезной нагрузки:
  `s/pa/ep/cr/up/mt/iw/ps` — сверено с разбором ccxt, `js/src/pro/binance.js`), и раньше на
  их месте стояли жёсткие нули. Ноль неотличим от настоящего нуля, поэтому сторож
  ликвидации, сравнивая с нулём, не срабатывал никогда. Пусто означает «биржа этого не
  сообщила»; нужно точное значение — читать позицию отдельным запросом. Bybit эти три
  сообщает и отдаёт как прежде. (`src/types/common.ts`, `src/exchanges/BinanceBaseClient.ts`,
  `src/exchanges/BybitBaseClient.ts`)
- **BREAKING: у записи средств поля стали `number | null` и добавилось «всего на кошельке».**
  Биржи сообщают РАЗНОЕ: спот называет свободное и заблокированное, фьючерсы — остаток
  кошелька. Выдавать недостающее нулями значило бы придумывать числа.
  (`src/types/common.ts`)
- **Сборщик заявок Bybit больше не выдаёт скользящий стоп за обычный.** Попытка собрать его
  обычной заявкой бросает ошибку — это закрывает и пакетный путь, который зовёт сборщик
  напрямую. (`src/exchanges/BybitBaseClient.ts`)

### Fixed

- **Сумма в котируемой валюте принимается только на РЫНОЧНОЙ заявке — на обеих биржах.**
  Единственный признак биржи, разрешающий такую сумму, называется «разрешено для рыночных»,
  лимитного соответствия у него нет (сверено с данными биржи 08.08.2026). Раньше обе биржи
  молча принимали её и на лимитной: Binance отправлял заявку ВООБЩЕ БЕЗ ОБЪЁМА, Bybit
  принимал сумму денег за количество монет.
  (`src/exchanges/BinanceBaseClient.ts`, `src/exchanges/BybitBaseClient.ts`)
- **Итогов закрытия у спота Bybit нет — говорим это прямо.** Проверено живым запросом:
  биржа отвечает «Closed pnl not support category». Раньше наружу шёл невнятный биржевой
  код; теперь ответ такой же, как у спота соседней биржи. (`src/exchanges/BybitBaseClient.ts`)
- **Ставка комиссии у Binance требует символ — говорим это прямо.** Проверено живым запросом:
  без символа биржа отвечает -1102. Соседняя биржа отдаёт ставки по всем символам сразу
  (831 запись), поэтому о разнице сказано явно, а не пропущен биржевой код.
  (`src/exchanges/BinanceFutures.ts`)
- **Ожидание готовности потоков у Bybit стало настоящим.** Метода не было вовсе, и базовый
  класс отдавал уже решённое обещание: бот считал потоки готовыми и начинал торговать на
  пустом кэше. Теперь ожидание идёт до фактического открытия соединений, как у соседней
  биржи. (`src/ws/BybitPublicStream.ts`, `src/ws/BybitPublicStream.types.ts`)
- **Предел частоты заявок у Bybit берётся с биржи, а не из числа в коде.** Биржа называет его
  заголовком ответа на заявку, и торговый канал этот заголовок уже разбирал — теперь значение
  запоминается и предпочитается. Число в коде осталось запасным вариантом, пока биржа своего
  не назвала. (`src/ws/BybitTradeStream.ts`, `src/exchanges/BybitBaseClient.ts`)
- **Клайны истории Bybit сообщают время закрытия.** Биржа его не присылает, но оно однозначно
  выводится из начала и длительности интервала; на его месте стоял ноль, и обходной приём
  «если ноль — посчитай сам» разошёлся по ТРЁМ приложениям сразу. Число сделок и объёмы
  покупателей Bybit не сообщает вовсе — это единственные поля клайна, которых у него нет.
  (`src/normalizers/bybitNormalizer.ts`, `src/constants/bybit.ts`)
- **Демо-режим Bybit предупреждает о себе вслух.** Торгового канала в демо биржа не даёт
  («WS Trade is not supported» в её документации), поэтому заявки идут обычными запросами —
  то есть проверенное в демо в бою исполняется другим путём. Обойти это нечем, но следствие
  теперь видно в журнале при запуске. (`src/exchanges/BybitBaseClient.ts`)
- **Тихие пустышки вокруг стакана убраны.** Пометка «живого» символа и подписка на сырой
  поток вызывались через необязательный доступ: если поток их не умеет, код отрабатывал
  молча — данных нет, ошибки нет. Теперь всё, что обещает доставку данных, отказывает
  громко; отписка и переподписка остаются тихими, потому что это уборка, а не обещание.
  (`src/exchanges/BaseExchangeClient.ts`)
- **Прочитанный с Bybit собственный стоп больше не выглядит обычной заявкой.** Bybit держит
  «условность» в ОТДЕЛЬНОМ поле: у защитной заявки `orderType` остаётся Market/Limit, а видом
  защиты служит `stopOrderType` — оно не читалось вовсе. Проверено на живой заявке 08.08.2026
  (`orderType=Market`, `stopOrderType=Stop`), у обычной поле пустое. Теперь тип складывается
  из обоих полей, а признак условности проставляется. Незнакомый вид защиты остаётся защитой:
  принять его за обычную заявку — самая опасная из ошибок здесь.
  (`src/normalizers/bybitNormalizer.ts`)
- **Признак условности проставляется и у Binance** — выводится из типа заявки.
  (`src/normalizers/binanceNormalizer.ts`)
- **Условные заявки спота Binance ищутся по типу, а не по цене срабатывания.** Домашнее
  условие «цена срабатывания больше нуля» делало заявку с нулевой ценой невидимой.
  (`src/exchanges/BinanceBaseClient.ts`)
- **Пакетная отмена на Binance снимает и условные заявки.** Они живут в отдельной службе, и
  пакетный вход обычной книги их не видит — просили снять пачку стопов, часть оставалась
  висеть. Известные условные снимаются по одной их собственным входом, без лишнего
  перечитывания заявки обратно. (`src/exchanges/BinanceFutures.ts`)
- **Границы времени доезжают до Bybit в истории заявок и в итогах закрытия.** Раньше молча
  выбрасывались, и «сделки за вчера» отдавали последние N записей независимо от дат. Проверено
  живым запросом 08.08.2026: обе ручки окно принимают и уважают — узкое окно вернуло одну
  запись вместо пяти. (`src/exchanges/BybitBaseClient.ts`, `src/http/BybitHttpClient.ts`)
- **Журнал начислений Bybit больше не отдаёт молча усечённый ответ.** Умолчание биржи — 20
  записей на страницу, постраничного дочитывания здесь нет: теперь всегда запрашивается
  максимальная страница, а полная страница считается признаком неполноты и вызывает отказ.
  Раньше отказ срабатывал, только если вызывающий сам назвал предел. (`src/exchanges/BybitBaseClient.ts`)
- **⚠️ Смена режима маржи на Bybit перестала быть пустышкой.** Метод писал строчку в журнал и
  не делал НИЧЕГО: потребитель просил изолированную маржу перед рискованным входом, счёт
  оставался в прежнем режиме, и узнать об этом было неоткуда. Теперь режим действительно
  переключается. **Внимание: на едином счёте Bybit это настройка ВСЕГО счёта, а не символа**
  (проверено живым чтением 08.08.2026: `marginMode=ISOLATED_MARGIN`, `unifiedMarginStatus=5`),
  поэтому переключение сопровождается громким предупреждением в журнал. Текущий режим
  сначала читается: если он уже нужный, запись не делается вовсе. (`src/exchanges/BybitLinear.ts`)
- **Номер стороны позиции у Binance заполняется на ВСЕХ путях чтения.** Три метода дописывали
  его вручную, четвёртый забывал — в двустороннем режиме читатель не понимал, какую из двух
  позиций ему дали. Значение выводится там же, где разбирается сама позиция, поэтому ручные
  дописывания удалены. Заодно односторонняя позиция помечается нулём — тем же числом, что и
  у соседней биржи (раньше у Binance там было пусто).
  (`src/normalizers/binanceNormalizer.ts`, `src/constants/mappings.ts`, `src/exchanges/BinanceFutures.ts`)
- **Binance выбрасывал провалившиеся заявки из ответа.** Ответ становился короче запроса,
  порядок съезжал, и исход приписывался соседней заявке. Дополнительно: условные заявки
  уходят отдельным путём и возвращались вперемешку с обычными — теперь каждый исход кладётся
  на СВОЁ место. Отказ одной условной заявки больше не уничтожает ответ по остальным: часть
  пачки к этому моменту уже стоит на бирже, и потерять её из ответа значит оставить живые
  заявки без управления. Ответ короче запроса тоже считается отказом, а не успехом.
  (`src/exchanges/BinanceFutures.ts`)
- **Bybit возвращал провал как успех.** Исход каждой заявки Bybit кладёт отдельным списком,
  выровненным с ответом по месту (документация batch-place), и этот список не читался вовсе —
  отказ приходил «открытой» заявкой с пустым номером, а вызывающий считал стоп поставленным.

  `src/ws/BybitTradeStream.ts`, `src/normalizers/batchOrderOutcome.ts`)
- **«Закрыть всю позицию» на Bybit больше не выбрасывается молча.** У Binance намерение

  позиция оставалась без защиты. По документации Bybit это нулевой объём вместе с двумя
  признаками закрывающей заявки — так теперь и собирается. (`src/exchanges/BybitBaseClient.ts`)

### Notes

- **Демо-режим Bybit**: это решение БИРЖИ, а не наш недосмотр: демо-торговля Bybit не поддерживает
  торговый канал. Исправить нельзя, поэтому сделано видимым.

    валовой минус чистый равен всей комиссии сделки.
  - Смысл поля «сторона» — сторона ЗАКРЫВАЮЩЕЙ заявки.
  - В журнале операций Bybit `cashFlow` — реализованный итог без комиссии, комиссия отдельным
    полем. Тождество `change = cashFlow + funding − fee` сошлось на живой записи до восьмого
    знака. Наружу комиссия отдаётся со знаком Binance (списано = минус).

Новый custom-subscriber `publicTrade` работает рядом с существующим `TradeToKlineAggregator` — оба consumer'а получают сообщения независимо; topic снимается только когда отписались оба.

#### Rate-limit visibility (per-UID + per-order runtime)

- `ExchangeClient.getOrderRateLimit(): Promise<OrderRateLimit>` — возвращает per-UID write rate-limit для order endpoints (статический снимок из exchange-info). Тип `OrderRateLimit { writeRequestsPerSecond: number; source: OrderRateLimitSource }`, где `OrderRateLimitSource = 'binance-exchange-info' | 'bybit-documented' | 'fallback'`.
- Binance Futures/Spot реализация: `parseBinanceOrderRateLimit(raw: BinanceExchangeInfoRaw)` (`src/normalizers/binanceNormalizer.ts`) фильтрует `rateLimits[].rateLimitType === 'ORDERS'`, конвертирует все интервалы в RPS, берёт `Math.min(...)` (наиболее строгий лимит). Если в `/fapi/v1/exchangeInfo` или `/api/v3/exchangeInfo` нет `rateLimits` — возвращает `{ writeRequestsPerSecond: BINANCE_ORDER_RATE_LIMIT_FALLBACK_RPS, source: 'fallback' }` (15 RPS). Новый raw-тип `BinanceRateLimitRaw { rateLimitType, interval: 'SECOND'|'MINUTE'|'HOUR'|'DAY', intervalNum, limit }`; `BinanceExchangeInfoRaw` расширен опциональным `rateLimits?`.
- Bybit Linear/Spot реализация: hardcoded `{ writeRequestsPerSecond: 20, source: 'bybit-documented' }` — Bybit не отдаёт rate-limits через GET endpoint, только через headers на actual order calls. Документированный лимит для `/v5/order/create`, `/v5/order/cancel`, `/v5/order/create-batch`, `/v5/order/cancel-batch` = 20 RPS per-UID (источник: https://bybit-exchange.github.io/docs/v5/rate-limit).
- Default throw `getOrderRateLimit()` в `BaseExchangeClient`; реализация на уровне `BinanceBaseClient` + `BybitBaseClient`.
- `OrderRateLimitSnapshot { limit, remaining, resetMs }` в `src/types/common.ts` — per-response runtime snapshot из заголовков ответа на одиночные order-операции через WebSocket Trade Stream. Опциональное поле `Order.rateLimit?` заполняется автоматически.
- `BybitTradeStream.handleSingleOrderResponse` парсит `message.header` через `parseBybitHeaderRateLimit` (`X-Bapi-Limit`, `X-Bapi-Limit-Status`, `X-Bapi-Limit-Reset-Timestamp` → `{ limit, remaining, resetMs }`). Новый тип `BybitTradeResponseHeader` в `BybitTradeStream.types.ts`.
- `BinanceTradeStream.handleMessage` парсит `message.rateLimits` через `parseBinanceRateLimitArray` (ищет entry с `rateLimitType === 'ORDERS' && interval === 'SECOND'` → `{ limit, remaining: limit - count, resetMs: now + intervalNum * 1000 }`). Новый тип `BinanceWebSocketRateLimitEntry` в `BinanceTradeStream.types.ts`.

### Changed

- `BinanceFutures.createBatchOrders` теперь чанкает входной массив по 5 ордеров (`BINANCE_FUTURES_CREATE_BATCH_CHUNK_SIZE`). Раньше отправлял всё одним запросом — при >5 ордеров Binance отвергал запрос. Кроме того, per-order ошибки в ответе Binance (`{code, msg}`) теперь логируются как `warning` и пропускаются — раньше падали на `normalizeBinanceOrder` со сломанным объектом.

- `BybitBaseClient.cancelBatchOrders`: добавлен early-return `[]` для пустого input до debug-лога. Маппинг success/error через `retExtInfo.list[i].code === 0` сохранён байт-в-байт.

- `BybitPublicStream.handleMessage`: ветка `topic.startsWith('orderbook.')` обрабатывается ДО проверки `Array.isArray(message.data)` — Bybit отдаёт `data` как объект (не массив) для orderbook-сообщений.

- `BybitPublicStream.resubscribeStream` / `BinanceFuturesPublicStream.resubscribeStream`: вместо безусловного `recreateConnection` теперь используется conditional light-resubscribe — `unsubscribe` + `subscribe` для подключённых сокетов, `recreateConnection` как fallback при ошибке отправки или `WebSocketStatus !== CONNECTED`. Снижает overhead на принудительной переподписке к одному topic, сохраняет recreate-семантику для отказных соединений.
- `BaseHttpClient.get`: в финальном `throw` (catch-блок retry-цикла) ошибка обогащается через `this.enrichError(axiosError)` — единый формат `Error("[code] msg")` или `Error("HTTP {status}: {message}")` вместо raw `AxiosError`.

### Changed (BREAKING)

- `ExchangeClient.cancelBatchOrders(symbol, orderIdList)` — сигнатура возврата изменена с `Promise<void>` на `Promise<CancelBatchOrdersResult>` (`= CancelOrderItemResult[]`). Каждый элемент содержит `{ orderId, isSuccess, errorCode: number | null, errorText: string | null }` для per-order трассировки результата. Consumer'ам, которые игнорировали возврат, миграция не требуется; те, кто ожидал `void` в type-checking — пометьте возврат явно или используйте `await` без присваивания.

### Notes

- **Binance Spot batch API не существует** на стороне биржи — `modifyBatchOrders`, `createBatchOrders`, `cancelBatchOrders` на Binance Spot бросают `Not supported for spot market` (наследуется default throw из `BaseExchangeClient`).
- **Binance Futures WebSocket API не имеет batch-методов** — только одиночные `order.place`, `order.modify`, `order.cancel`. Verified: URLs `Place-Multiple-Orders` / `Modify-Multiple-Orders` / `Cancel-Multiple-Orders` в Binance WebSocket API docs возвращают 404. Batch на Binance идёт только через REST.

  - Ticker price updates (Binance Futures)
- Type-safe unified types:
  - `Kline` — candlestick data
  - `Ticker` — current price and 24h change
  - `Position` — futures position details
  - `Order` — placed order info
  - `Market` — market metadata
  - `Balance` — account balance
- Automatic WebSocket reconnection with exponential backoff
- Structured logging via custom logger interface
- Price and amount precision formatting
- Error normalization across exchanges

### Internal
- Separate HTTP clients for each exchange
- Exchange-specific normalizers (Binance and Bybit)
- Public and private WebSocket streams
- Auth utilities (HMAC signing, headers)
- Four exchange implementations: BinanceFutures, BinanceSpot, BybitLinear, BybitSpot
- Factory pattern via unified `Exchange` entry point

### Notes
- Binance spot and futures use separate rate limits
- Bybit combines spot and linear in single unified API
- Public endpoints (markets, klines) do not require API keys
- Private endpoints (balance, position, orders) require valid credentials
- WebSocket subscriptions are stateless and can be re-established on reconnect
